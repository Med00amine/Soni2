# Soni2 — repository audit (2026-10-20)

Baseline recorded before any code change in this session.

## Actual architecture

```
backend/app/
  main.py                 FastAPI app + the whole pipeline (1403 lines)
  jobs.py                 SQLite durable job/sentence/event store + pronunciation lexicon
  book_structure.py       Parsers: PDF (PyMuPDF), EPUB (EbookLib), DOCX (python-docx), XML (DTBook-ish), TXT
  narration_plan.py       Section classification (TOC / front / synopsis / intro / main / back)
  sentences.py            Stable sentence IDs + offsets; pronunciation lexicon applied to TTS copy only
  spanish_normalization.py Spanish-aware canonical tokens for QA comparison
  daisy_export.py         DAISY 3 package builder (DTBook + SMIL + NCX + OPF + RES)
  daisy_validation.py     Custom structural/reference validation of the generated package
frontend/src/
  App.tsx                 Entire UI (542 lines), 3 tabs: upload / review / export
  api.ts, types.ts        DEAD: client for endpoints that do not exist in this backend
  styles.css              DEAD: not imported anywhere
```

### Execution flow (upload → audiobook)

1. `POST /api/books/structure` — parse, classify sections, return plan + default selection.
2. `POST /api/books/preview` — parse, apply selection, synthesize the first `PREVIEW_CHARACTERS` (5000) characters, request ASR word timestamps for highlighting.
3. `POST /api/books/jobs` — parse, apply selection + paragraph corrections, segment into sentences with stable IDs, persist job to SQLite, start an in-process asyncio task.
4. `run_production_job` — per sentence: synthesize (up to 1 + 5 retries, exponential backoff) → ASR transcribe → Spanish-aware compare → ffmpeg acoustic heuristics → up to 3 quality retakes → else `needs_human_review`.
5. `POST /api/jobs/{id}/review` — human accepts / retries / corrects a sentence; job requeues.
6. `_assemble_job_delivery` — joins sentence audio into chapter audio and a full book, builds the DAISY package, validates it, writes reports, zips everything.
7. `POST /api/books/package` — a separate, synchronous, **uncached** full-book path that regenerates every paragraph.

### Provider integrations

Fish Audio is the only provider, used for **both** TTS (`/v1/tts`, model `drama-3`) and ASR (`/v1/asr`, model `transcribe-1`). There is no ElevenLabs, Deepgram or MeloTTS code despite the commit message "Restore ElevenLabs narration". There is no mock/offline mode, so nothing in the audio path can be exercised without a funded Fish Audio account.

## Critical production gaps

| # | Severity | Problem |
|---|---|---|
| P1 | blocker | Single hard-coded provider. `synthesize()` raises "Fish Audio is the only configured narration provider." With Fish credits exhausted the entire audio pipeline is dead, and there is no offline/mock mode to develop or test against. |
| P2 | high | Default voice/language is **es-MX** (`FISH_AUDIO_LANGUAGE=es-MX`, default voice "Rodrigo"/Mexico). The product targets Spain. The frontend sorts Spain voices first but the server default and `/api/capabilities.voice` stay Mexican. No accent validation before expensive generation. |
| P3 | high | **No audio cache whatsoever.** Sentence IDs are stable, but reuse exists only *within one job row* (`state == verified`). Re-uploading the same book regenerates everything. `/api/books/package` regenerates the whole book on every call. Every preview click re-synthesizes 5000 characters. Each sentence costs up to 6 TTS calls × 4 quality retakes **plus** a paid ASR call per generation. Nothing guards against duplicate concurrent requests. |
| P4 | high | PDF ingestion makes one pseudo-chapter per page titled `Página N`, which `_category()` cannot classify, so it defaults to `main` → **title pages, copyright pages and contents pages get narrated**. This is the reported "starts narrating the table of contents" defect. |
| P5 | high | `job.log` is JSON Lines, not a human-readable log, and the separate `tts-log.json` carries no diagnostics. No provider/operation/cache/validation detail, so you cannot tell why a sentence failed or whether audio was reused. |
| P6 | high | `quality-report.html` is an unstyled 6-column table that dumps raw JSON into a cell. No summary, metadata, voice/provider, chapter grouping, filters, audio, or validation outcome. |
| P7 | medium | QA collapses every difference into `likely_mismatch` / `likely_error`. There is no "ambiguous, needs human review" outcome, even though the frontend already has a label for it. Confidence is a crude token-count ratio. |
| P8 | medium | DAISY output stores each chapter's audio **three times** (`audio/chapter-NNNN.mp3`, `audio/chapter-NNN/chapter-NNNN.mp3`, `audio/chapter-NNN/chapter-NNN.mp3`), every sentence **twice** (`audio/segment-*.mp3` + per-chapter folder), and the full book twice (`book.mp3`, `full-audiobook.mp3`). The delivery ZIP then adds the job's sentence audio a further time. |
| P9 | medium | No incremental rebuild. One corrected sentence triggers a full `rmtree` of `delivery/`, re-encode of every chapter, re-encode of the full book, full DAISY rebuild and full re-zip. |
| P10 | medium | No atomic writes. `destination.write_bytes(chosen_audio)` overwrites known-good audio in place; reports and logs are written non-atomically. An interrupted job can leave corrupt artifacts. |
| P11 | low | `/api/capabilities` reports `automatic_audio_review: false` and `retakes: false`, but the production pipeline does both. |
| P12 | low | Dead code: `_tts_chunks` (duplicates the chunker inlined in `synthesize`), `frontend/src/api.ts` + `types.ts` (endpoints that do not exist), `frontend/src/styles.css` (not imported). |

## Security / configuration check

- `.env` **is** git-ignored and is not tracked. No secret values were printed or committed during this audit.
- `.env.example` carries no real credentials (empty `FISH_AUDIO_API_KEY`).
- No paid provider call was made while establishing this baseline.

## Implementation priorities

1. Provider abstraction: separate TTS from ASR, add Deepgram ASR + TTS and an offline `mock` provider, with classified user-facing errors. (P1)
2. Content-addressed audio cache + per-sentence reuse across jobs, previews and packages; duplicate-request guard. (P3)
3. Spain-Spanish voice default and pre-generation accent validation. (P2)
4. Confidence-aware QA outcomes including an explicit ambiguous/review class. (P7)
5. Content-based front-matter and contents-page detection so narration starts at the narrative. (P4)
6. Human-readable `job.log` alongside structured events. (P5)
7. A real quality report. (P6)
8. De-duplicated output layout, atomic writes, incremental chapter/book/DAISY rebuild. (P8–P10)
9. Capability honesty and dead-code removal. (P11, P12)
10. Offline regression tests across all of the above. (Phase 8)
